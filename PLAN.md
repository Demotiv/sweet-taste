## 1. Что это

Однопользовательское офлайн-приложение для кондитера на Windows:
учёт текущих и прошлых заказов, личная книга рецептов, ценообразование по закупкам ингредиентов.

Не коммерческий продукт, делается под конкретного человека.
Стиль утверждён (см. §6). Старый прототип лежит в `D:\OpenCode\SweetTaste.Draft` как донор, в новый проект не копируется.

Текущая версия — Windows-приложение. Направления развития (веб-версия для iPhone,
синхронизация, альфа-выпуск и установщик) собраны в §9.

## 2. Зафиксированные решения

- Платформа: Windows, .NET 8, Avalonia UI (XAML), MVVM (CommunityToolkit.Mvvm).
- Логика отдельно от UI: проект `Core`, покрывается юнит-тестами (xUnit).
- Хранение: локальная база SQLite + ежедневный бэкап (реализовано).
- Синхронизация с телефоном — позже; модель данных дружелюбна к синхронизации (Guid, метки времени).
- Ингредиент — одна карточка товара на всё время, без дублей на каждую покупку.
- Категории ингредиентов: кондитер создаёт сам из формы; список сгруппирован по категориям,
  категории раскрываются. В выпадающих списках ингредиенты тоже идут группами по категориям.
- Удаление ингредиента/рецепта — в корзину с подтверждением; окончательное удаление — уже из корзины.
- Удаление категории: ингредиенты/рецепты переходят в «Без категории», ничего не теряется.
  Категории ингредиентов и рецептов удаляются и переименовываются из заголовка группы.
- Корзина: удалённые ингредиенты и рецепты хранятся отдельно; можно восстановить или удалить навсегда.
  Закупки и состав рецепта сохраняются до окончательного удаления.
- Заказ: нумеруется, хранит клиента (имя, фамилия, телефон), дату выдачи, состав (рецепт + количество),
  статус, комментарий и зафиксированную сумму.
- Статусы: Новый → Готовится → Готов → Выдан, плюс Отменён; текущие и архив.
- Список покупок под заказ агрегирует ингредиенты по составу и считает примерную сумму по средним ценам.
- Закупка — отдельная запись журнала: дата, магазин, объём, сумма. Может ссылаться на заказ (необязательно).
- Закупка вводится как «объём + всего потрачено»; магазин — текстом, справочник позже.
- Средняя цена ингредиента — взвешенная: сумма потраченных денег / суммарный объём.
- История цен: наведение на цену показывает последнюю закупку, клик — всю историю.
- Рецепт: состав (пока без технологии), фиксированный выход в штуках или весе (кг/г),
  наценка. Вес может быть дробным: партия торта 2,5 кг.
- Заказ: клиент (имя, фамилия, телефон), строки «рецепт + количество», дата выдачи, статус, итоговая цена.
  Количество — в единицах выхода рецепта: только целые штуки или дробный вес (1,5 кг).
- Состав и список покупок под заказ масштабируются: коэффициент = заказано / выход партии.
  «Порции» как единица выхода больше не используются; старые данные переведены в штуки.
- Цена заказа рассчитывается из себестоимости и наценки, но фиксируется в заказе (историю не пересчитываем).
  Цена за штуку и килограмм округляется вверх до рубля, за грамм — до копейки.
- Упаковка — отдельный справочник в разделе «Ингредиенты» (кнопка «Упаковки»):
  категории коробок, название, размер и закупочная цена.
- Упаковка выбирается в «Деталях» заказа после списка покупок, с количеством; кнопка «Без упаковки» очищает выбор.
- К цене упаковки применяется средневзвешенная наценка рецептов заказа
  (выручка рецептов / их себестоимость); изменения в деталях сохраняются сразу.
- В существующих заказах упаковка остаётся снимком: название, размер, цена и количество не меняются.
- Позиции заказа с одним и тем же рецептом не склеиваются: каждый торт — отдельная строка.
  Ингредиенты в «Что купить» считаются и показываются по каждой позиции отдельно, плюс общий итог.
- Настройки: тема (светлая / тёмная / как в системе), резервные копии и значения по умолчанию.
- Тёмная тема — тёплая шоколадная; цвета вынесены в общие токены, переключение мгновенное, без перезапуска.
- Настройки хранятся в базе (`app_settings`) и попадают в бэкап.
- Резервные копии: срок хранения настраивается (7/14/30/90 дней), есть ручной бэкап с меткой времени.
- Новые рецепты получают наценку и единицу выхода из настроек; существующие рецепты не меняются.
- Профиль кондитера: название кондитерской, имя, Instagram, Telegram, сайт и логотип/фото.
- Профиль — одна запись в базе; фото хранится в самой базе и попадает в бэкап.
- Название и имя показываются в боковом меню, фото — в карточке профиля и внизу меню.
- Все бизнес-данные привязаны к профилю через `profile_id`: ингредиенты, закупки, рецепты,
  заказы, категории и упаковка. Пока профиль один (id = 1), но модель готова к нескольким.
- В настройках есть опасная зона «Удаление заказов»: «Очистить архив» удаляет выданные
  и отменённые заказы (отчёты строятся по ним, поэтому обнуляются), «Удалить все заказы» —
  все заказы. Вторая кнопка доступна, только когда есть текущие заказы. Оба действия
  необратимы и требуют подтверждения.
- Клиенты: отдельная база, номер выдаётся при первом заказе; клиент находится по телефону
  или фамилии, данные подставляются в форму заказа.
- Заказ связан с клиентом; имя и телефон в заказе остаются снимком, карточка клиента обновляется.
- Клиента можно удалить: его заказы остаются в истории, но теряют привязку к карточке.
  При новом заказе с тем же телефоном клиент создаётся заново.
- Из карточки клиента по нажатию на заказ открываются детали этого заказа.
- В деталях заказа видны номер клиента, дата создания, оплата, остаток и вся информация о заказе.
- Отчёты: вкладка «Клиенты» с числом заказов, выручкой, средним чеком и последним заказом.
- Графики: топ рецептов по количеству, выручка по дням, «кто заказывает чаще».
- Клиенты привязаны к профилю через `profile_id`.
- В профиле есть «Перенос данных»: полная копия базы выгружается в выбранную папку
  (флешка, другой диск) вместе с короткой инструкцией по восстановлению на другом ПК.
- В настройках есть восстановление базы из файла: проверка, что это SQLite, автоматический бэкап
  текущей базы и замена с предложением перезапустить приложение.
- Клиенты: вкладка в заказах, карточка с историей и кнопками «Новый заказ» и «Повторить последний».
- Список покупок: галочки «куплено», копирование в буфер и открытие текстового файла для печати.
- Оплата заказа: предоплата, остаток к оплате и отметка «оплачен».
- При создании заказа предоплата по умолчанию — 50% итога; сумму можно изменить вручную.
- Итоговая сумма заказа округляется вверх до целого рубля; старые заказы приведены к этому правилу миграцией.
- Скидка на заказ: уменьшает итог, фиксируется в заказе и не меняет рецепты.
- При запуске показывается напоминание о заказах на сегодня и завтра.
- Напоминание пересчитывается при любом изменении заказов: новый заказ, смена статуса,
  отмена и выдача. Закрытые заказы в него не попадают, поэтому после выдачи оно исчезает.
- В деталях заказа статус можно переключить на любой: Новый, Готовится, Готов, Выдан,
  Отменён. Так исправляется случайное нажатие, а заказ возвращается из архива в текущие.
- Рецепт хранит технологию приготовления и фото; фото видно в книге рецептов.
- Нажатие на рецепт в любом месте строки (кроме кнопок изменения и удаления) открывает карточку
  просмотра: фото, состав с суммами, расчёт и технология пошагово. Шаги берутся из поля
  «Технология приготовления» — каждая непустая строка это шаг; из карточки можно перейти
  к редактированию.
- «Без категории» — служебная группа: её нельзя создать или переименовать в неё категорию.
- В форме рецепта есть пересчёт состава под другое количество — подсказка для заказа.
- Отчёты выгружаются в CSV для Excel и в HTML для печати/PDF.
- Печатный отчёт — строгая серая таблица без терракотовых акцентов.
- Масштаб интерфейса 90–125% в настройках; окно подстраивается под экран.
- Категории ингредиентов и рецептов можно переименовывать.
- Списки рецептов и упаковок собраны в раскрывающиеся группы по категориям, как справочник
  ингредиентов: нажатие на категорию показывает её содержимое и количество позиций.
  В рецептах фильтр по категории заменён группами, категорию можно переименовать или удалить
  прямо из заголовка группы.
- Отчёты: выручка, прибыль, количество заказов, популярные позиции, затраты за период.
- Отчёты считаются по дате выдачи и только по выданным заказам; период — месяц по умолчанию,
  плюс неделя, год и произвольный диапазон.
- Прибыль — выручка минус себестоимость на момент оформления заказа: при создании заказа
  себестоимость фиксируется снимком и позже не меняется (старые заказы восстановлены приблизительно).
- Экспорт отчётов в Excel/PDF — отдельным этапом позже.
- Деньги: рубли. Единицы: г, мл, шт (при необходимости кг/л).
- Сборка приложения — по кирпичам: каждый этап оставляет рабочую версию.
- Автообновление: при запуске проверяются GitHub Releases. Новая версия скачивается
  по кнопке «Обновить», проверяется SHA-256 и устанавливается после закрытия приложения.
  Данные в `%APPDATA%` не меняются, перед заменой создаётся копия базы.
- Проверка обновлений использует Atom-ленту GitHub Releases и не расходует лимит API;
  обычный API остаётся запасным вариантом. В настройках есть кнопка «Проверить обновления».

## 4. Текущий статус

**Windows-версия завершена в текущем объёме.** Работает весь основной цикл:
ингредиенты и закупки → рецепты с весом → клиенты → заказы с упаковкой →
отчёты с графиками → профиль, тема, бэкапы и выгрузка данных.

Логика — 208 тестов; UI проверен вручную на основных сценариях.
На странице «Ингредиенты» карточка ингредиента открывается нажатием на любую часть строки.
На странице «Заказы» детали заказа открываются нажатием на любую часть строки.
Просмотровые окна закрываются кликом по затемнённому фону; формы и подтверждения — нет.
Собрана версия `0.5.0`: self-contained ZIP для Windows x64, без установки .NET.
В приложении есть автоматическая проверка обновлений на GitHub.
В «Настройках» есть вход в аккаунт Supabase; при закрытии приложение выгружает
снапшот данных в облако. Без входа и без сети программа работает как раньше.
Windows-приложение можно использовать как есть; веб-версия и синхронизация — отдельные идеи в §9.

Кирпич 4 готов: отчёты за период (неделя, месяц, год или произвольный диапазон).
Считаются выручка, прибыль, число заказов, средний чек, затраты на закупки, топ рецептов и разбивка по дням.
Период — по дате выдачи, в выручку попадают только выданные заказы; заказы в работе показаны отдельной подсказкой.
Себестоимость фиксируется в заказе снимком (миграция v6), поэтому прошлые отчёты не пересчитываются
при изменении цен; у старых заказов она восстановлена приблизительно и помечена в отчёте.

Рецепты и заказы работают с весом: выход партии задаётся в шт, кг или г и может быть дробным;
количество в заказе — в тех же единицах (1,5 кг), состав и покупки масштабируются пропорционально.
Старые рецепты и заказы переведены из «порций» в штуки (миграция v7).

Упаковка вынесена в отдельный справочник: категории, коробки с размером и закупочной ценой.
В деталях заказа коробки выбираются с количеством, итог пересчитывается и сохраняется сразу;
к цене коробки применяется средневзвешенная наценка блюд заказа.
Одинаковые рецепты в заказе остаются отдельными позициями: ингредиенты в «Что купить»
считаются и показываются для каждого торта отдельно, общий итог — внизу.

Раздел «Настройки»: светлая, тёмная или системная тема; срок хранения резервных копий и ручной бэкап;
наценка и единица выхода по умолчанию для новых рецептов. Настройки сохраняются в базе.
Тёмная тема — тёплая шоколадная, переключается сразу.

Раздел «Профиль»: название кондитерской, имя, Instagram, Telegram, сайт и логотип.
Название и имя подставляются в боковое меню, фото уменьшается до 512 px и хранится в базе.
Все ингредиенты, рецепты, заказы, закупки и упаковка помечены `profile_id`; профиль пока один.

В настройках есть опасная зона «Удаление заказов»: «Очистить архив» удаляет выданные
и отменённые заказы (вместе с ними обнуляются отчёты), «Удалить все заказы» удаляет
и текущие. Кнопка полного удаления активна только при наличии текущих заказов.
Действия необратимы, выполняются через подтверждение.

Добавлена база клиентов: при первом заказе клиенту выдаётся номер, телефон нормализуется
(8 и +7 считаются одним номером). В форме заказа по телефону или фамилии появляются подсказки
из базы, по нажатию подставляются имя, фамилия и телефон.
В отчётах появилась вкладка «Клиенты» и диаграммы: топ рецептов по количеству,
выручка по дням и «кто заказывает чаще».

В профиле можно выгрузить полную базу в выбранную папку — для флешки или переноса на другой ПК.
Рядом сохраняется `sweet-taste-README.txt` с инструкцией, как заменить базу.

В заказах появилась вкладка «Клиенты»: карточка клиента с историей заказов и кнопкой
«Повторить последний» — форма открывается с тем же составом и клиентом.
Из карточки можно провалиться в любой заказ клиента и удалить клиента;
заказы при удалении остаются в истории без привязки к карточке.
Список покупок получил галочки «куплено», копирование и открытие текстового файла для печати.
У заказа есть предоплата, остаток к оплате и отметка «оплачен».
В настройках можно восстановить базу из файла: перед заменой создаётся бэкап текущей.

Добавлен второй круг улучшений: скидка на заказ, напоминание о выдачах на сегодня и завтра,
технология и фото рецепта, пересчёт состава под другое количество, экспорт отчётов в CSV и для печати,
масштаб интерфейса 90–125% и переименование категорий.

Списки рецептов и упаковок собраны в раскрывающиеся группы по категориям, как справочник ингредиентов:
заголовок показывает число позиций, нажатие раскрывает содержимое. В рецептах фильтр по категории
заменён группами, категорию можно переименовать или удалить прямо из заголовка; отдельная кнопка
«Категории» убрана.

Просмотр рецепта: нажатие в любом месте строки (кроме кнопок изменения и удаления) открывает карточку
с фото, выходом, наценкой, себестоимостью, ценой, составом и пошаговой технологией. Шаги — непустые строки поля «Технология приготовления»,
нумерация и маркеры списка при показе убираются. Из карточки можно сразу перейти к редактированию.
Служебное имя «Без категории» запрещено для реальных категорий ингредиентов, рецептов и упаковки.

Напоминание о выдачах пересчитывается при добавлении заказа, смене статуса и отмене:
выданные и отменённые заказы в него не входят, поэтому после выдачи оно исчезает.
В деталях заказа появился выбор статуса: Новый, Готовится, Готов, Выдан, Отменён.
Любой статус можно поставить повторно — это исправляет случайное нажатие и возвращает
заказ из архива в текущие.

Сборка: self-contained ZIP `win-x64`, SHA-256, README, ярлык и `Update.cmd`
с сохранением предыдущей версии для отката. Версия `0.2.0` показана внизу бокового меню;
иконка приложения — терракотовый квадрат с «ST». Данные по-прежнему лежат в `%APPDATA%\SweetTaste`.

Автообновление: при запуске приложение читает Atom-ленту GitHub Releases (без лимита API),
сравнивает версии с учётом pre-release и показывает баннер. Обычный API используется как
запасной вариант. В «Настройках» есть кнопка «Проверить обновления» с тем же результатом.

Что осознанно не сделано:
- сохранение пересчитанного состава под конкретный заказ (в книге рецепт остаётся на партию);

  идемпотентны и применяются в этом порядке через SQL Editor панели.
- В облаке 13 таблиц + `sync_state`; у каждой составной PK `(user_id, id)` и RLS-политика
  `own_rows` (`for all to authenticated`, `using` + `with check` по `auth.uid()`).
  `sync_state` — одна строка на пользователя, PK = `user_id` без default.
- Внешние ключи составные по `(user_id, ...)`, чтобы строки разных пользователей не могли
  ссылаться друг на друга. Для обнуления ссылки используется `on delete set null (<колонка>)`:
  обычный `set null` обнулил бы и `user_id`, который объявлен `not null`.
- `purchases.order_id` намеренно без FK: закупка может быть вне заказа.
- `service_role` / secret key в клиент и репозиторий не попадают; в приложении только
  publishable-ключ. Регистрация закрыта — аккаунт создаётся вручную в панели Supabase.
- Проверка облака без входа: `GET /rest/v1/<таблица>` с заголовком `apikey` → `200 []`,
  `POST` → `42501 new row violates row-level security policy`.
- Снапшот: `Sync/SyncSnapshot.cs` — 12 таблиц бизнес-данных (без `app_settings` и
  `confectioner_profile`), `RowCounts` и `TotalRows` для сверки после загрузки.
  `Sync/SnapshotExporter.cs` читает всё в одной транзакции (`BeginTransaction(deferred: true)`),
  поэтому снапшот согласован. Фото рецепта кодируется в base64 (`PhotoBase64`).
- Количества в снапшоте — те же масштабированные целые, что в SQLite: `*_milli` для
  ингредиентов и заказов, но выход рецепта и состав хранятся в тысячных долях
  (2,5 кг → 2500), а количество в заказе — в целых единицах (2 шт → 2000).
- Вход: `Sync/SupabaseAuthClient.cs` — `POST /auth/v1/token?grant_type=password` и
  `grant_type=refresh_token`, заголовок `apikey` с publishable-ключом. Ошибки Supabase
  (`invalid_credentials`, `email_not_confirmed`, `over_request_rate_limit`) переводятся
  в русские сообщения через `AuthException` с полем `Code`. Пароль нигде не сохраняется.
- Сессия: `Sync/ProtectedSessionStore.cs` — файл `sync-session.bin` рядом с базой,
  зашифрован DPAPI (`DataProtectionScope.CurrentUser`) с энтропией
  `SweetTaste.Sync.Session.v1`. Запись через временный файл, чтобы обрыв не оставил
  битую сессию. Повреждённый или чужой файл считается отсутствием входа.
  Класс помечен `[SupportedOSPlatform("windows")]` — DPAPI есть только на Windows.
- `AuthSession.IsExpired` считает токен протухшим за минуту до `ExpiresAt` — запас на сеть.
- Пакет `System.Security.Cryptography.ProtectedData` 8.0.0 добавлен в `SweetTaste.Core.csproj`.
- Выгрузка: `Sync/SnapshotRows.cs` переводит снапшот в строки облачных таблиц
  (`user_id` не передаётся — его заполняет `auth.uid()`), `Sync/SyncService.cs` шлёт
  их в PostgREST. Порядок: удалить все строки пользователя в обратном порядке
  зависимостей, затем вставить по `SnapshotRows.LoadOrder`, в конце — `sync_state`
  с `Prefer: resolution=merge-duplicates`.
- `DELETE` в PostgREST требует условия, поэтому используется `?id=not.is.null`;
  RLS всё равно ограничивает удаление строками текущего пользователя.
- Фото уходит в `bytea` как hex с префиксом `\x`; `cost_estimated` — настоящий `boolean`;
  метки времени — ISO 8601 в UTC с микросекундами, даты — `yyyy-MM-dd`.
- Ошибки выгрузки — `SyncException` с полем `Table`: 401 → «Сессия истекла»,
  403 → подсказка про политики, остальное — текст `message` от PostgREST.
- Атомарная выгрузка: `supabase/003_sync_rpc.sql` создаёт `public.replace_snapshot(
  p_schema_version, p_taken_at, p_tables)` — `security invoker`, `search_path = public`.
  Удаляет строки пользователя в обратном порядке зависимостей, вставляет из
  `jsonb_to_recordset` в прямом (через четыре функции-помощника), пишет `sync_state`
  и возвращает счётчики строк. Всё в одной транзакции: обрыв сети не оставит
  облако пустым.
- `replace_snapshot` доступна только роли `authenticated` (`revoke` у `public` и `anon`).
  `user_id` берётся из `auth.uid()`, а не из тела запроса. Анонимный вызов даёт
  `401 permission denied for function replace_snapshot` — это и есть признак того,
  что функция создана и права выставлены верно (до создания было `404 PGRST202`).
- Файл `003` применяется пятью частями из `supabase/parts/` (`003_part1..5.sql`),
  как и `001`. **Резать тело функции нельзя**: часть с открывающей `$fn$` без
  закрывающей падает с `42601: unterminated dollar-quoted string at or near "$fn$"`
  ещё до выполнения. Поэтому `replace_snapshot` разложена на четыре
  функции-помощника (`_replace_snapshot_refs`, `_replace_snapshot_recipes`,
  `_replace_snapshot_orders`, `_replace_snapshot_packaging`) — каждая часть
  самостоятельный `create or replace function ... as $fn$ ... end; $fn$;` ≤100 строк,
  а пятая часть — сборная `replace_snapshot`: проверки, удаление, вызовы
  помощников, `sync_state`, `revoke`/`grant` для всех пяти функций.
  Помощники принимают `p_user_id` и `p_tables`, возвращают `jsonb` со счётчиками;
  `security invoker` у всех, поэтому RLS действует и внутри помощников.
  Права на помощников тоже сняты с `public`/`anon`: анонимный вызов любого из них
  даёт `401 permission denied for function ...`.
- **История снапшотов в облаке** (`supabase/004_snapshot_archive.sql`, три части
  `parts/004_part1..3.sql`). `replace_snapshot` стирает строки пользователя, поэтому
  предыдущее состояние облака исчезает; архив держит его копию.
  - `snapshot_archive`: `user_id`, `id`, `taken_at`, `schema_version`, `total_rows`,
    `row_counts jsonb`, `tables jsonb`, `archived_at`; PK `(user_id, id)`,
    индекс `ix_snapshot_archive_recent (user_id, archived_at desc)`, RLS `own_rows`.
  - `tables` — ровно та же форма, что `p_tables` у `replace_snapshot`
    (`{table: [row, ...]}`), поэтому восстановление переиспользует клиентский
    `SnapshotReader` без второго парсера.
  - `_archive_snapshot_tables(p_user_id)` (`language sql stable`) собирает 12 таблиц
    через `jsonb_agg(to_jsonb(t) - 'user_id' order by ...)`. `user_id` вырезан:
    владелец задан колонкой архива. Сортировка повторяет `SnapshotRows.LoadOrder`
    и `SnapshotExporter`, иначе сравнение на дубликат не сработает.
  - `archive_snapshot(p_keep integer default 10)` — `security invoker`, `$fn$`.
    `auth.uid()` пуст → `42501`. `set_config('bytea_output','hex',true)` — иначе
    `to_jsonb(photo)` даёт escape-формат вместо `\x...`. Возвращает
    `{archived:false, reason:no_state|empty|duplicate}` либо
    `{archived:true, id, taken_at, schema_version, total_rows, row_counts}`.
    Пустое облако не архивируется, идентичное состояние не дублируется — иначе
    окно истории вытесняется копиями. Обрезка до `p_keep` последних по `archived_at`.
  - Хранится 10 версий: фото 449 КБ → hex ≈ 898 КБ текста → ~450–600 КБ на диске,
    итого ≤6 МБ (≈1% бесплатных 500 МБ).
  - Порядок выгрузки: `archive_snapshot()` → `replace_snapshot()`. Если архив упал,
    замена не выполняется — облако остаётся нетронутым.
  - Клиент вызывает их одним методом `SyncService.UploadWithArchiveAsync(snapshot,
    session, keep, ct)`: сначала архив, затем замена. Транзакция на две RPC не одна
    намеренно — архив должен переживать неудачную замену, а замена без архива
    не начинается. Повтор после сбоя самолечится: нетронутое облако сервер вернёт
    как `duplicate`, и замена пройдёт. Оба ответа отдаются вызывающему
    (`UploadWithArchiveResult`), чтобы интерфейс показал, сохранилась ли копия.
- **Редактор SQL в панели Supabase обрезает текст на `$$`** — тело функции
  открывается и закрывается `$fn$`. Ошибка выглядит как
  `42601: unterminated dollar-quoted string at or near "$$"` с припиской
  `-- source: dashboard`. Тот же приём нужен для любой функции в панели.
- `SyncService.UploadAtomicAsync` шлёт один `POST /rest/v1/rpc/replace_snapshot`
  и берёт счётчики из ответа сервера; `UploadAsync` (поштучная загрузка) остаётся
  запасным путём.
- Архив читается теми же средствами, что и обычный снапшот:
  `SnapshotReader.ParseTables` переводит `snapshot_archive.tables` в строки через
  `ParseRows` (`Clone()` и `SyncException` в одном месте), затем
  `Read(tables, taken_at, schema_version)` собирает снапшот. Версия схемы берётся
  из строки архива: копию могли сделать прошлой версией приложения.
- `snapshot_archive` намеренно не входит ни в `SyncTables`, ни в `SnapshotRows.LoadOrder`:
  это метаданные облака, а не бизнес-данные, и в `p_tables` они не попадают.
- `ListArchivesAsync` запрашивает только `id,taken_at,schema_version,total_rows,archived_at`:
  каждый `tables` — сотни килобайт, и тянуть их на каждое открытие списка незачем.
- `SelectAsync` принимает полный путь с query (`"ingredients?select=*"`), поэтому
  запросы архива, списка версий и `sync_state` не дублируют HTTP-код.
- UI входа: `SettingsViewModel` принимает `SupabaseAuthClient` и `ISessionStore`,
  в конструкторе вызывает `RestoreSession()` — вход восстанавливается из
  `sync-session.bin` при каждом открытии страницы. `SignInCommand` (async) валидирует
  пустые поля, сохраняет сессию и стирает пароль из памяти; `SignOutCommand` удаляет
  файл сессии, локальные данные не трогает. Ошибки `AuthException` показываются
  в `SyncError` как есть — сообщения уже на русском.
- `SupabaseOptions` (URL + publishable key) создаётся константами в `App.axaml.cs`,
  без конфиг-файла: ключ публичный по определению, секретов в клиенте нет.
- `SweetTaste.Desktop.csproj` получил `SupportedOSPlatformVersion=7.0` и
  `TargetPlatformIdentifier=Windows`: без них CA1416 ругался на
  `ProtectedSessionStore.CreateDefault` в `App.axaml.cs`. Приложение и так
  Windows-only (DPAPI, автообновление через PowerShell).
- Выгрузка при выходе: `Sync/SyncOnExit.cs`, подписка на `desktop.ShutdownRequested`
  в `App.axaml.cs`. Нет сессии — выход без сети; протухший токен обновляется
  через `RefreshAsync` и сохраняется в `sync-session.bin`; затем
  `SnapshotExporter.Export` → `SyncService.UploadWithArchiveAsync`.
- **Deadlock при закрытии.** `SyncService` и `SupabaseAuthClient` ждут HTTP через
  `await _http.SendAsync(...)` без `ConfigureAwait(false)`, поэтому продолжения
  планировались в заблокированный UI-поток, а `ShutdownRequested` ждёт выгрузку
  синхронно — окно висело. Фикс минимальный: вся работа обёрнута в
  `Task.Run(...).GetAwaiter().GetResult()`, продолжения уходят в пул потоков.
  Править уже проверенные `SyncService`/`SupabaseAuthClient` не стали.
- Таймаут выгрузки — 45 с (`CancellationTokenSource`). При 5 с снапшот с base64-фото
  не успевал: на запрос уходило 0.3–2.4 с, и выгрузка падала с `TaskCanceledException`.
  До 45 с поднят, когда к замене добавился архивный запрос.
- `SyncOnExit` пишет диагностику в `%LOCALAPPDATA%\SweetTaste\sync.log` на каждом
  этапе (сессия загружена/нет, снапшот собран, итог архива, выгрузка завершена),
  а не только при исключении — иначе зависание не отличить от тихого отказа.
  При сбое архива в строку ошибки добавляется причина из `InnerException`:
  наружу отдаётся только «выгрузка отменена».
- Ошибка выгрузки не мешает закрытию: приложение закрывается, причина остаётся в логе.
  `AutoUpdate.ps1` ждёт закрытия процесса до 120 с, поэтому выгрузка при выходе
  обновление не ломает.
- **`GET /rest/v1/<таблица>` с publishable-ключом даёт `200 range=*/0` — это RLS,
  а не пустое облако.** Политика `own_rows` фильтрует по `auth.uid()`, у анонимного
  ключа сессии нет. Проверять данные только в панели Supabase (Table Editor)
  или под настоящей сессией.
- **Восстановление версии из истории** (`SettingsViewModel`, диалог «История облака»):
  `OpenArchiveAsync` только читает список (`ListArchivesAsync`) и открывает диалог —
  данные не меняются; ошибка чтения попадает в `ArchiveError` и диалог открывается
  с ней, пустой список — сообщение «В истории пока нет версий.» без диалога.
  `ConfirmRestoreArchiveAsync` закрывает диалог, читает снапшот по `SelectedArchive.Info.Id`
  и повторяет путь загрузки из облака: проверка `SchemaVersion` → `CreateBackupNow()`
  → `SnapshotImporter.Import` → сообщение с числом строк, датой версии и именем бэкапа.
  Ошибки восстановления идут в `SyncError` карточки, как у остальных действий синхронизации.
  `IsArchiveBusy` отделяет чтение списка от `IsSyncBusy`: список — не запись, и блокировать
  ради него кнопки выгрузки незачем.
- Список версий — `ArchiveOption` (в конце `SettingsViewModel.cs`, как `OrderRecipeOption`
  в `OrdersViewModel.cs`): поля `Info` и `Text`, `ToString()` отдаёт `Text`, поэтому
  `ComboBox` показывает версию без `ItemTemplate`.
- **Раскладка ZIP с 0.6.1: служебные файлы в `tools\`.** `README.txt`, `Update.cmd`,
  `Update.ps1`, `AutoUpdate.ps1`, `CreateShortcut.cmd` лежат в подпапке, в корне —
  только `SweetTaste.exe`, `createdump.exe`, два `.json` рантайма и `version.json`.
  `scripts/release.ps1` создаёт `$toolsDir` и копирует туда пять файлов, текстовые
  правки (`Set-ReleaseTextFile`) идут по тому же пути.
- **`AutoUpdate.ps1` ищется в двух местах.** `UpdateService.UpdaterScriptPath` проверяет
  корень, затем `tools\`; `CanSelfUpdate` — это `UpdaterScriptPath is not null`.
  Двойной поиск нужен для перехода: версия 0.6.0 ищет скрипт только в корне, и без
  запасного пути она не увидела бы обновление. `StartUpdater` берёт скрипт из
  `UpdaterScriptPath`, дублирующая проверка убрана.
- `Update.ps1` и `AutoUpdate.ps1` правок не потребовали: `-AppDir` приходит снаружи
  (`Update.cmd` передаёт `%~dp0..`, приложение — `AppDirectory`), `version.json`
  и `SweetTaste.exe` ищутся в `$AppDir`, папка заменяется целиком — подпапка `tools\`
  переносится автоматически.
- `Update.cmd` и `CreateShortcut.cmd` считают папку программы как `%~dp0..`:
  `%~dp0` уже оканчивается на `\`, поэтому `..` даёт родителя папки `tools`.
  Запускать их нужно из `tools\`, а не из корня — из корня `%~dp0..` укажет на папку
  выше программы.

## 6. Стиль

Утверждён: **«Патиссерия»** (макет: `docs/style/preview.html`).
Тёплая кремовая основа, шоколадный текст, терракота как единственный акцент,
тонкие линии, лёгкие тени, скругления 9–14 px, без анимаций размера текста.
Шрифты: **PT Serif** (заголовки, кириллица) + **Fira Sans** (интерфейс) — статические TTF, надёжно встраиваются.

Правило выравнивания (глобально, для всех текущих и будущих форм):
текст в `TextBox`, `ComboBox` и внутреннем `TextBox` у `NumericUpDown` выровнен по центру по вертикали.
Новые формы наследуют это автоматически, отдельно настраивать не нужно.

Правило скругления (глобально): все контролы и поповеры скруглены.
`ControlCornerRadius` = 8, `OverlayCornerRadius` = 14; кнопки 7–9, карточки 10–14.
Новые элементы делаем скруглёнными, без острых углов.

Правило курсора (глобально): всё, что нажимается, показывает курсор-руку — кнопки, вкладки,
выпадающие списки, поля даты и календарь, флажки, переключатели, строки списков.
У выключенных элементов курсор обычный. Новые контролы наследуют это автоматически.

Активный пункт бокового меню: тёплый терракотовый фон и акцентный текст; неактивные — вторичный цвет.

Выбор даты: компактный поповер 248×236, числа по центру, стрелки и кнопки подтверждения скруглены,
разделители колонок одного цвета, поле даты не выходит за свою колонку.

Числовые поля: кнопки-стрелки (`NumericUpDown`) и их hover/pressed-подсветка скруглены.
Дробные значения принимаются и с запятой, и с точкой (2,5 и 2.5); показываются с запятой.
Выпадающие списки (`ComboBox`): поповер скруглён, тёплый фон, выбранный пункт — скруглённая плашка.

Токены:
- фон `#EDE4D8`, поверхность `#FFFCF8`, вторичный фон `#F8F2E9`;
- текст `#2E211B`, вторичный `#6E5D52`, линии `#E9DDCE`;
- акцент `#B25B39`, карамель `#C98A4B`, шалфей `#7C8B6B`;
- успех `#4F7A4A`, предупреждение `#B67A22`, ошибка `#A5433A`, инфо `#5A7C93`.

Тёмная тема: тёплый шоколад — фон `#1B1512`, поверхности `#261E1A` и `#2D2420`,
текст `#F3E9DF`, вторичный `#CBB9AA`, линии `#3A2E27`, акцент `#D47A52`.
Все цвета — в токенах, поэтому светлая, тёмная и системная темы переключаются мгновенно.

## 7. Структура проекта

  `003_sync_rpc.sql` (выгрузка), `004_snapshot_archive.sql` (история снапшотов);

## 9. Идеи на будущее

Ниже — направления, которые обсуждались, но не входят в завершённую Windows-версию.
Они не блокируют использование программы.

### 9.1. Веб-версия для iPhone

**Зачем.** У девушки iPhone; Windows-приложение на iOS не запускается, а собирать нативное iOS-приложение
сложно и дорого. Достаточно адаптивного сайта/PWA: открывается в Safari, ставится иконкой на домашний экран.

**Что это значит.** Это не порт, а вторая реализация: Avalonia-интерфейс и локальный SQLite-файл
в браузере не работают, а текущая вёрстка 1340×840 не подходит под телефон.

**Рекомендуемый стек.**
- Фронтенд: React + TypeScript, mobile-first PWA, те же токены «Патиссерии», PT Serif + Fira Sans.
- Бэкенд: Supabase — PostgreSQL, Auth (email-ссылка/код), Storage для логотипа, REST/Realtime.
- Хостинг: Cloudflare Pages / Netlify / Vercel — бесплатно, HTTPS, свой адрес.
- Данные: облако — источник истины; локальный кэш (service worker + IndexedDB) для просмотра и скорости.
- Авторизация: один общий аккаунт или личные аккаунты; доступ через RLS по `user_id`.
- Синхронизация: `updated_at`, правило «последняя правка побеждает», Guid-id, мягкое удаление;
  одновременные правки одного заказа редки.

**Бесплатные лимиты.** Supabase free: 500 МБ базы, 1 ГБ файлов; проект засыпает после недели простоя
(при ежедневном использовании незаметно). Хостинг фронтенда бесплатный.

**Офлайн.** Интерфейс и данные кэшируются, без сети можно открыть и посмотреть. Полноценная работа
офлайн на iOS ограничена: нет фоновой синхронизации, браузер может очищать хранилище.
Проще и надёжнее — онлайн-first с кэшем.

**Что переносим.**
- ингредиенты, закупки, средняя цена;
- рецепты, вес, наценка, себестоимость;
- клиенты, заказы, упаковка;
- отчёты и графики (SQL-агрегаты);
- профиль и фото — в Supabase Storage.

**Этапы.**
1. PWA-каркас: навигация, тема, вход, деплой.
2. Ингредиенты и закупки.
3. Рецепты.
4. Клиенты, заказы, упаковка.
5. Отчёты и графики.
6. Импорт текущей базы и — при необходимости — синхронизация с Windows-версией.
7. Полировка: кэш, ошибки сети, восстановление данных.

**Варианты синхронизации с ПК.**
- Веб — основной клиент, Windows-версию подключаем к той же облачной базе.
- Веб только для телефона, обмен с ПК через экспорт/импорт — проще и быстрее.
- Веб становится основной версией, Windows-версия постепенно уходит.

**Альтернативы.**
- Avalonia WebAssembly: переиспользует C# и UI, но остаётся десктопная вёрстка, тяжёлая загрузка,
  а хранилище и синхронизацию всё равно переделывать — для iPhone не рекомендуем.
- Blazor WebAssembly: C#/Razor, но новый UI и хранилище; тяжелее React.
- Blazor Server/ASP.NET + SQLite: переиспользует Core, но бесплатный хостинг обычно без постоянного диска;
  нужен внешний PostgreSQL.
- Firebase: сильный офлайн-SDK, но привязка к Google и неудобные SQL-отчёты.
- Свой мини-сервер: контроль, но free-тарифы часто без постоянного диска.

**Риски.**
- две кодовые базы и две поддержки;
- данные в облаке: нужны RLS, бэкапы и понятная политика приватности;
- free-тарифы могут меняться или засыпать;
- ограничения PWA на iOS;
- бизнес-логику придётся продублировать на TypeScript и покрыть тестами.

**Что решить перед стартом.** Нужна ли синхронизация с ПК? Насколько важен офлайн?
Один аккаунт или личные? Supabase или Firebase? Готовы ли держать данные в облаке?

### 9.2. Сборка и обновления

**Статус: 0.6.1 опубликована.** Self-contained ZIP `win-x64`, без установщика.
Репозиторий и релизы: `https://github.com/Demotiv/sweet-taste`.
Релиз `v0.6.1` опубликован как latest вместе с ZIP и SHA-256; CI и Release зелёные.
С главной страницы репозитория доступна постоянная ссылка
`releases/latest/download/SweetTaste-win-x64.zip` — её обновляет release workflow.

- Сборка одной командой: `pwsh -File scripts/release.ps1`
  (тесты → publish → папка релиза → ZIP → SHA-256).
- GitHub Actions: `.github/workflows/ci.yml` собирает проект и гоняет тесты,
  `.github/workflows/release.yml` по тегу `v<версия>` собирает ZIP и публикует
  GitHub Release с SHA-256, заметками из `docs/releases/<версия>.md` и постоянными
  `SweetTaste-win-x64.zip` / `.sha256` для ссылки на главной странице.
- Проверка релиза: `gh run list --limit 3` (статус CI/Release) и
  `gh release view v<версия> --json tagName,isPrerelease,assets` (ассеты).
  GitHub CLI 2.105.0 установлен через winget, вход выполнен под `Demotiv`.
- Экшены workflow: `actions/checkout@v7`, `actions/setup-dotnet@v6` (Node 24).
  `checkout@v7` блокирует checkout форков в `pull_request_target`/`workflow_run` —
  эти триггеры не используются. `setup-dotnet@v6` перешёл на ESM; `global.json`
  в проекте нет, поэтому ужесточение проверки `sdk.version` не затрагивает.
- Результат: `dist/SweetTaste-0.6.1-win-x64.zip` (~46 МБ)
  и `SweetTaste-0.6.1-win-x64.zip.sha256`.
- Автообновление: `UpdateService` проверяет Atom-ленту GitHub Releases (запасной вариант — API),
  `UpdateVersion` сравнивает версии с pre-release, ZIP скачивается с проверкой SHA-256;
  `AutoUpdate.ps1` заменяет файлы после закрытия приложения и запускает новую версию.
  Ручная проверка — в «Настройках», кнопка «Проверить обновления».
- Внутри: в корне — `SweetTaste.exe` (apphost переименован для человека), `createdump.exe`,
  `SweetTaste.Desktop.deps.json`, `SweetTaste.Desktop.runtimeconfig.json`, `version.json`
  (версия, схема БД, дата); в подпапке `tools\` — `README.txt`, `Update.cmd`, `Update.ps1`,
  `AutoUpdate.ps1`, `CreateShortcut.cmd`. Всего 229 файлов (219 `.dll`, 2 `.exe`, 3 `.json`).
- Служебные файлы в `tools\` с версии 0.6.1: `Update.cmd` и `CreateShortcut.cmd` считают
  папку программы как `%~dp0..`, поэтому запускать их нужно из `tools\`.
  `UpdateService` ищет `AutoUpdate.ps1` сначала в корне, затем в `tools\` — так версия 0.6.0
  (которая знает только корень) тоже видит обновление.
- Self-contained — .NET 8 на компьютере не требуется; только Windows 10/11 x64.
- Данные лежат в `%APPDATA%\SweetTaste`, поэтому замена папки приложения их не затрагивает.
- Обновление: автоматически из баннера (проверка GitHub, скачивание, SHA-256,
  замена файлов и перезапуск) или вручную — закрыть приложение и перетащить ZIP на `Update.cmd`.
  Оба способа сохраняют текущую папку как `<имя>-old-<версия>-<дата>`.
  Откат — вернуть старое имя папки; данные при этом не трогаются.
- Миграции базы односторонние: перед обновлением — бэкап; откат приложения
  без отката базы не гарантирован.
- Версию показывают подпись внизу бокового меню и `version.json`; иконка — `ST`.
- Неподписанный `.exe` вызывает предупреждение SmartScreen; для альфы допустимо,
  для чужих людей — сертификат.
- Позже: Inno Setup (классический установщик), Velopack (дельта-обновления
  и установщик), MSIX (требует сертификат), GitHub Actions по тегу.

**Чек-лист релиза.**
1. Поднять `<Version>` в `SweetTaste.Desktop.csproj`.
2. `pwsh -File scripts/release.ps1` — тесты входят в сборку.
3. Проверить ZIP на чистой базе: первый запуск, миграции, создание заказа.
4. Приложить ZIP и SHA-256 к релизу, описать изменения.
5. Напомнить про бэкап перед обновлением.
